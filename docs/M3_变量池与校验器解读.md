# M3 变量池与校验器解读

本文用于精读 Smart-Workflow 的 M3 代码，覆盖：

- `internal/engine/varpool/pool.go`：运行时变量池 VariablePool
- `internal/engine/varpool/path.go`：引用路径解析 `result.segments[0].text`
- `internal/engine/varpool/validate_out.go`：节点输出 JSON Schema 校验
- `internal/engine/varpool/varpool_test.go`：变量池测试（对标 PaiFlow VariablePoolTest）
- `internal/validator/validator.go`：静态校验器 Validator
- `internal/validator/validator_test.go`：校验器测试
- `internal/dsl/deps.go`：执行依赖构建 `edges ∪ bindings` 与环检测

M3 的核心目标：

```text
在“不运行工作流”的前提下，把坏图挡在保存/发布之前（静态校验）；
在“运行工作流”的时候，给节点之间提供一块并发安全的共享内存（变量池）；
并给出连接两者的地基：执行依赖 = edges ∪ ref bindings。
```

---

## 1. 先回答几个最容易混淆的问题

### 1.1 变量池是持久化存储吗？和 M2 的表是什么关系？

不是。变量池不落库。

M2 讲的是“把 DSL 存进 MySQL”，那是**持久化**。M3 的变量池是**一次运行期间的临时内存**：

```text
workflow.draft_dsl / workflow_version.dsl   ← M2，落库，长期存在
VariablePool                                ← M3，内存，一次 run 用完即弃
```

源码里说得很直接（`pool.go`）：

```go
// VariablePool 是工作流的运行时共享内存（设计文档 §7）。
// 两层映射：nodeID -> (outputName -> value)。并发安全。
// 它是一次运行的临时产物，不落库。
type VariablePool struct {
    mu   sync.RWMutex
    vars map[string]map[string]any
}
```

那节点的 input/output 到底要不要落库？要，但那是另一件事：

```text
变量池           = 运行中节点之间传值的内存池（M3，不落库）
node_run.input/output = 运行结束后落库的执行快照（M2 建表，M4 写入）
```

换句话说：变量池负责“运行时把值传下去”，`node_run` 负责“运行后把值记下来”。两者内容相关，但生命周期和存储介质完全不同。

### 1.2 变量池的 key 是 IR 的可读 ID 还是 DSL 的执行态 ID？

是 DSL 执行态 ID，比如 `start::start0`、`application::a1b2c3`。

原因很简单：**变量池只在运行期出现**，而运行期用的是 render 之后的 DSL。M1 讲过：

```text
IR ID  = start_0            给 Agent/CLI 看
DSL ID = start::start0      给引擎/存储/运行看
```

测试里也能直接看出来（`varpool_test.go`）：

```go
p.Set("node-start::001", "user_input", "请介绍一下Java")
p.Set("node-llm::002", "response", map[string]any{...})
```

调度器写变量池时用的也是 DSL 节点 ID（`scheduler.go`）：

```go
c.pool.SetOutputs(id, result.Outputs) // id 是 DSL 节点 ID
```

所以记住这个分界：

```text
校验器（M3 上半场）跑在 IR 上，用可读 ID。
变量池（M3 下半场）跑在运行期，用 DSL ID。
```

### 1.3 校验器 Validate 吃的是 IR 还是 DSL？

吃 IR。

这点非常关键，也最容易搞反。看入口签名（`validator.go`）：

```go
func Validate(ir *dsl.IR) *Result
```

它要的是编辑态 IR，不是执行态 DSL。为什么？因为 M1 已经解释过：**IR 才带端口声明、扁平 binding、可读 ID，适合逐点定位问题**；DSL 是编译产物，binding 已经内联进 `schema.value`，反而不好校验。

于是就出现一个乍看奇怪、其实合理的调用模式（`internal/service/validate.go`）：

```go
// 校验器吃编辑态 IR，故先把存储的 DSL 反渲染成 IR 再校验。
ir, err := dsl.ToIR(d, meta)
...
return validator.Validate(ir)
```

也就是说：

```text
CLI 场景：本地 session 里本来就有 IR，直接 validator.Validate(s.IR)
服务端场景：库里存的是 DSL，先 ToIR 反编译回 IR，再 Validate
```

M1 里讲的 `ToIR`（DSL→IR 反编译器），在这里第一次派上了正经用场。

### 1.4 error 和 warning 有什么区别？

`error` 必须修到 0 才能保存/发布；`warning` 是建议性提示，不阻断。

结构上用 `Severity` 区分（`validator.go`）：

```go
const (
    SeverityError   Severity = "error"
    SeverityWarning Severity = "warning"
)
```

判定“能不能过”的只有一个方法：

```go
func (r *Result) HasError() bool {
    for _, i := range r.Issues {
        if i.Severity == SeverityError {
            return true
        }
    }
    return false
}
```

注意：`HasError` 只看 error，不看 warning。所以：

```text
有 3 个 warning、0 个 error  -> HasError() = false -> 可以过
有 0 个 warning、1 个 error  -> HasError() = true  -> 不能过
```

当前唯一的 warning 是 `unreachable_node`（孤立节点）。其余检查项都是 error 级。

### 1.5 环检测为什么基于 `edges ∪ bindings`，而不是只看 edges？

因为“数据引用”本身就是一种“执行依赖”，只看控制流边会漏。

M1 的 `deps.go` 讲过一个核心公式：

```text
执行依赖 = 显式 edges ∪ 由 ref bindings 推导的隐式边
```

考虑这种坏图：

```text
没有边 A -> B
但 B 的某个输入 ref 了 A 的输出
```

如果环检测只看 edges，就发现不了“B 依赖 A”这条隐式边。M3 的 `checkCycle` 直接复用 M1 的依赖构建（`validator.go`）：

```go
func checkCycle(ir *dsl.IR, r *Result) {
    if dsl.HasCycle(dsl.BuildDeps(ir)) {
        r.add(SeverityError, "cycle", "", "", "workflow graph has a cycle")
    }
}
```

`BuildDeps` 把 edge 依赖和 ref binding 依赖合并成一张图，`HasCycle` 用 Kahn 拓扑排序判环。这样即使你没画边，只要 A、B 互相 ref，也会被判成环。

### 1.6 `result.segments[0].text` 这种引用路径是怎么解析的？

分两步：先把字符串解析成 token 序列，再从值上逐步 walk 下去。

第一步 `parsePath`（`path.go`）把路径切成 token：

```text
"result.segments[0].text"
  -> [field:result, field:segments, index:0, field:text]
```

第二步 `walkPath` 从根值出发，逐个 token 取值：

```text
field  -> 当前值必须是 map[string]any，按 key 取
index  -> 当前值必须是 []any，按下标取
```

任何一步类型不符或越界，都返回明确错误。这套设计直接对标 PaiFlow 的 `VariablePoolTest`，M3 把它翻成了 Go 表驱动测试（见第 9 节）。

需要强调一个约定：**路径第一段必须是端口名**（field），不能上来就是下标：

```go
if tokens[0].isIdx {
    return nil, fmt.Errorf("invalid ref %q: must start with a port name", name)
}
```

因为变量池第一层永远是 `outputName -> value`，端口名是入口。

## 2. M3 的整体架构

M3 有两根支柱，分别服务两个不同的时刻：

```text
                编辑/保存时刻                      运行时刻
                （不运行工作流）                   （真正执行）
                     |                                |
                     v                                v
              +--------------+                 +----------------+
              |  Validator   |                 |  VariablePool  |
              | 静态校验器    |                 |  运行时变量池   |
              +--------------+                 +----------------+
                     |                                |
                     | 吃 IR                          | 存 DSL节点ID -> 输出
                     v                                v
       结构/字段/绑定/引用/环/可达性            节点间传值 + 输出校验
```

两根支柱靠一块公共地基连起来——**执行依赖构建**（M1 的 `deps.go`）：

```text
Validator 用它做环检测、可达性分析
Scheduler（M4）用它决定节点调度顺序
```

核心文件：

```text
internal/engine/varpool/pool.go          # 变量池主体
internal/engine/varpool/path.go          # 引用路径解析
internal/engine/varpool/validate_out.go  # 输出类型/必填校验
internal/validator/validator.go          # 静态校验器
internal/dsl/deps.go                      # 执行依赖 + 环检测（M1 已建，M3 复用）
```

一句话概括分工：

```text
Validator 负责“运行前别让坏图进来”。
VariablePool 负责“运行时把值安全地传下去”。
deps.go 负责“告诉大家谁依赖谁”。
```

## 3. 为什么校验器吃 IR，不吃 DSL？

这是 M3 最重要的设计决策，值得单独展开。

M1 说过 render 不做完整校验：

```text
render 只做结构转换：IR -> DSL
不负责完整业务校验。完整校验由 M3 的 validator 做。
```

那校验为什么放在 IR 层，而不是 DSL 层？三个理由：

```text
1. IR 有端口声明。IR 的 Node 带 Inputs/Outputs（Port{name,type,required}），
   校验器才能查“ref 的 source_port 到底存不存在”“类型兼不兼容”。
2. IR 的 binding 是扁平的。一条 binding 就是一行 {port, source_node, source_port}，
   报错能精确定位到“哪个节点的哪个端口”。DSL 里 binding 内联进 schema.value，嵌套很深。
3. IR 用可读 ID。报错信息里写 app_1 比写 application::a1b2c3 对人和 Agent 都友好。
```

代价是：库里存的是 DSL，服务端校验时必须先 `ToIR`。但这个代价很小，而且 M1 的反编译器本来就要为 `clone-ref` 准备，顺便复用。

于是形成两条校验入口：

```text
CLI（本地 session 已有 IR）：
  validator.Validate(s.IR)              直接校验，零成本、秒级

服务端（库里是 DSL）：
  dsl.ToIR(dsl) -> validator.Validate(ir)   先反编译再校验
```

`validateDSL` 还做了一个细节处理——`ToIR` 失败也归一成一条 error（`validate.go`）：

```go
ir, err := dsl.ToIR(d, meta)
if err != nil {
    return &validator.Result{Issues: []validator.Issue{{
        Code:     "dsl_to_ir_failed",
        Severity: validator.SeverityError,
        Message:  err.Error(),
    }}}
}
```

这样调用方永远拿到结构化的 `Result`，而不是有时拿 `Result`、有时拿裸 `error`。

## 4. 变量池 VariablePool 详解

源码：`internal/engine/varpool/pool.go`

### 4.1 数据结构

```go
type VariablePool struct {
    mu   sync.RWMutex
    vars map[string]map[string]any
}
```

| 字段 | 用途 |
|---|---|
| `mu` | 读写锁，保证并发节点同时读写安全 |
| `vars` | 两层映射：`nodeID -> (outputName -> value)` |

两层映射的含义：

```text
vars["application::a1b2c3"]["label"]      = "positive"
vars["application::a1b2c3"]["confidence"] = 0.92
vars["start::start0"]["query"]            = "这家餐厅很好吃"
```

第一层 key 是 DSL 节点 ID，第二层 key 是该节点的输出端口名。

为什么要加 `RWMutex`？因为 M4 的调度器是并发的：多个没有依赖关系的节点会同时跑，同时往变量池写自己的输出、读上游的输出。没有锁就会 data race。

### 4.2 写入：Set / SetOutputs / SetError

单个写入：

```go
func (p *VariablePool) Set(nodeID, name string, val any) {
    p.mu.Lock()
    defer p.mu.Unlock()
    if p.vars[nodeID] == nil {
        p.vars[nodeID] = make(map[string]any)
    }
    p.vars[nodeID][name] = val
}
```

批量写入（节点跑完一次性写所有输出）：

```go
func (p *VariablePool) SetOutputs(nodeID string, outputs map[string]any)
```

写系统错误变量：

```go
func (p *VariablePool) SetError(nodeID string, code any, message string)
```

`SetError` 写的是两个特殊端口：

```go
const (
    SysErrorCode    = "errorCode"
    SysErrorMessage = "errorMessage"
)
```

用途：节点失败后，失败分支或兜底逻辑可以 ref 到 `errorCode`/`errorMessage`。这对齐了 PaiFlow 的“系统输出变量”设计——每个节点执行后，这两个变量自动可用。

调度器里的用法（`scheduler.go`）：

```go
if execErr != nil {
    c.pool.SetError(id, "NODE_ERROR", execErr.Error())  // 失败：写错误变量
} else {
    c.pool.SetOutputs(id, result.Outputs)                // 成功：写输出
}
```

### 4.3 读取：Get / Resolve / Has

`Get` 是核心，支持路径：

```go
func (p *VariablePool) Get(nodeID, name string) (any, error)
```

它的逻辑：

```text
1. 加读锁
2. 找到 nodeID 对应的内层 map，没有就报 "node has no variables"
3. parsePath(name) 把 name 切成 token 序列
4. 第一个 token 必须是端口名（field），不能是下标
5. 取出端口对应的根值 root
6. 如果只有一个 token，直接返回 root
7. 否则 walkPath(root, tokens[1:]) 逐步深入
```

`Resolve` 只是 `Get` 的语义别名，给“引用视图”用：

```go
func (p *VariablePool) Resolve(nodeID, portPath string) (any, error) {
    return p.Get(nodeID, portPath)
}
```

M4 的 `ResolveInputs` 就是靠它把 ref binding 变成具体值（`builder/resolve.go`）：

```go
val, err := pool.Resolve(rc.NodeID, rc.Name)  // rc 来自 DSL 的 RefContent
```

`Has` 判断端口是否存在，不解析路径（只看第一段）：

```go
func (p *VariablePool) Has(nodeID, port string) bool
```

它会把带路径的 `port` 截到第一段：

```go
head := port
if i := strings.IndexAny(port, ".["); i >= 0 {
    head = port[:i]
}
```

也就是 `Has("n", "result.segments[0].text")` 只检查 `n` 有没有 `result` 这个端口，不深入路径。

### 4.4 Snapshot：为什么要深拷贝？

```go
func (p *VariablePool) Snapshot() map[string]map[string]any
```

它返回变量池的**深拷贝**，用于持久化 / 暂停恢复 / 调试。

为什么必须深拷贝？测试说明了原因（`varpool_test.go`）：

```go
func TestPool_Snapshot(t *testing.T) {
    p := New()
    p.Set("n", "k", "v")
    snap := p.Snapshot()
    snap["n"]["k"] = "mutated" // 改快照不应影响池
    if v, _ := p.Get("n", "k"); v != "v" {
        t.Errorf("snapshot not isolated: %v", v)
    }
}
```

如果只做浅拷贝，外部拿到快照后改一个值，会连带把池里的值也改了。深拷贝保证快照是“只读镜像”，改它不影响正在运行的池。

注意：Snapshot 只深拷贝了两层 map 结构，**值本身（如嵌套的 map/slice）还是共享引用**。对当前“记录标量输出”的用途够用，但如果值是可变的大对象，仍需留意。

## 5. 引用路径解析：parsePath 与 walkPath

源码：`internal/engine/varpool/path.go`

这是变量池最“像编译器”的部分，也是对标 PaiFlow `VariablePoolTest` 的关键。

### 5.1 token 结构

```go
type token struct {
    key   string // 字段名（isIdx=false 时有效）
    index int    // 数组下标（isIdx=true 时有效）
    isIdx bool
}
```

一个 token 要么是“字段名”，要么是“数组下标”，用 `isIdx` 区分。

### 5.2 parsePath：字符串 -> token 序列

```text
"result.segments[0].text"
  按 '.' 切段: ["result", "segments[0]", "text"]
  每段再解析尾部的 [i]:
    "result"      -> field:result
    "segments[0]" -> field:segments, index:0
    "text"        -> field:text
  最终: [field:result, field:segments, index:0, field:text]
```

它能处理三种写法的混合：

```text
a.b        纯字段
a[0]       字段 + 下标
a.b[0].c   混合
```

解析中会拦截各种非法输入：

```text
空路径              -> "empty path"
空段（如 a..b）     -> "empty segment"
下标缺 ]（如 a[0） -> "missing ']'"
下标非数字或为负     -> "bad index"
```

### 5.3 walkPath：从根值逐步取值

```go
func walkPath(root any, tokens []token) (any, error)
```

规则很简单，但类型检查很严：

```text
遇到 index token：当前值必须是 []any，否则报 "expected array"
                  下标越界报 "index out of range"
遇到 field token：当前值必须是 map[string]any，否则报 "expected object"
                  key 不存在报 "key not found"
```

为什么 map 只认 `map[string]any`、数组只认 `[]any`？因为这些值大多来自 JSON 反序列化，Go 的 `encoding/json` 默认就把对象解成 `map[string]any`、数组解成 `[]any`、数字解成 `float64`。变量池按这个“JSON 通用形态”工作，跨语言（Go/Python sidecar）传值才一致。

## 6. 输出校验 ValidateOutputs

源码：`internal/engine/varpool/validate_out.go`

这是 M3 的“输出 JSON Schema 校验”，对标 PaiFlow `VariablePool.do_validate` 的轻量版。

### 6.1 它做什么

```go
func ValidateOutputs(outputs map[string]any, decls []dsl.Port) []string
```

给定“节点实际产出的 outputs”和“节点声明的输出端口 decls”，逐条检查：

```text
1. 声明为 required 的端口，实际没产出 -> "missing required output"
2. 端口有值，但类型和声明不符       -> "type mismatch"
```

返回所有问题字符串；空切片表示通过。

### 6.2 类型匹配规则

```go
func typeMatches(t string, v any) bool
```

按 JSON 反序列化后的通用形态判断：

| 声明类型 | 接受的 Go 类型 |
|---|---|
| `string` | `string` |
| `boolean` | `bool` |
| `number` | `float64/float32/int/int32/int64` |
| `integer` | 整数，或“恰好是整数值的 float64” |
| `array` | `[]any` |
| `object` | `map[string]any` |

两个细节：

```text
v == nil 一律放过，交给 required 逻辑处理（null 不算类型错）。
未知声明类型不拦（default 返回 true），宽松兜底。
```

`integer` 的判断值得注意——因为 JSON 数字统一是 `float64`：

```go
case float64:
    return n == float64(int64(n)) // 3.0 算整数，3.5 不算
```

所以 `count=3.0` 通过整数校验，`count=3.5` 报 integer mismatch。

### 6.3 它和静态校验器的类型检查有什么区别？

这两处都在“查类型”，但时机和对象不同，别混：

```text
validator 的 type_mismatch（第 5 节）：
  静态、编辑期，比对“声明 vs 声明”
  —— 上游 output 声明的类型 vs 下游 input 声明的类型

ValidateOutputs（本节）：
  运行期，比对“实际值 vs 声明”
  —— 节点真跑出来的值 vs 该节点 output 端口声明的类型
```

一个是“图还没跑，先查连线合不合理”；一个是“节点跑完了，查产出对不对得上契约”。

## 7. 静态校验器 Validator 详解

源码：`internal/validator/validator.go`

### 7.1 Issue / Result / Severity

一条问题：

```go
type Issue struct {
    Code     string   `json:"code"`     // 机器可识别的问题码
    Severity Severity `json:"severity"` // error / warning
    Node     string   `json:"node,omitempty"`   // 定位到哪个节点
    Field    string   `json:"field,omitempty"`  // 定位到哪个字段/端口
    Message  string   `json:"message"`  // 人类可读描述
}
```

汇总结果：

```go
type Result struct {
    Issues []Issue `json:"issues"`
}
```

这个结构的设计意图很明确：

```text
Code   给 Agent/程序判断“是哪类问题”，可分类自动修复
Node/Field 给 CLI/画布逐点定位（跳到出错的节点和端口）
Message 给人看
Severity 决定是否阻断（HasError）
```

### 7.2 Validate 主流程

```go
func Validate(ir *dsl.IR) *Result {
    r := &Result{}
    nodeByID := indexNodes(ir, r)   // 建索引 + 查重复/空 ID

    checkStartEnd(ir, r)            // start 恰好 1 个、end 至少 1 个
    checkKindAndFields(ir, r)       // 类型受支持 + 字段与 kind 匹配
    checkEdges(ir, nodeByID, r)     // 边端点存在、无自环
    checkCycle(ir, r)               // 基于 edges∪bindings 检测环
    checkBindings(ir, nodeByID, r)  // 必填绑定、ref 指向、类型兼容、作用域
    checkReachability(ir, nodeByID, r) // 从 start 可达（warning）

    return r
}
```

六个检查函数按顺序跑，各自往 `r.Issues` 追加问题。下面逐个看。

### 7.3 indexNodes：建索引 + 查 ID

```text
- 空 ID           -> error empty_node_id
- 重复 ID         -> error duplicate_node_id
- 正常            -> 存入 id->node 索引，供后续检查用
```

为什么先建索引？因为后面 `checkEdges`、`checkBindings` 都要频繁按 ID 查节点，建一次 map 比每次线性扫快。

### 7.4 checkStartEnd：起止节点约束

```go
if starts != 1 {
    r.add(SeverityError, "start_count", ...)   // 必须恰好 1 个 start
}
if ends < 1 {
    r.add(SeverityError, "end_missing", ...)   // 至少 1 个 end
}
```

规则：

```text
start：有且仅有 1 个（0 个或多个都报 start_count）
end：  至少 1 个（允许多个 end）
```

### 7.5 checkKindAndFields：类型受支持 + 字段合法性（改②）

先看类型是否在支持集合里：

```go
var supportedKinds = map[string]bool{
    KindStart: true, KindEnd: true, KindApplication: true,
    KindDataset: true, KindWorkflow: true, KindCondition: true, KindCode: true,
}
```

不在就报 `unsupported_node_type`。

然后做两件对称的事：

```text
A. field_not_allowed_for_kind：不该带的专属字段带了就报
   start 节点带了 app_id      -> 报错
   condition 节点带了 dataset_id -> 报错

B. missing_xxx_id：该带的专属字段没带就报
   application 节点没 app_id      -> missing_app_id
   dataset 节点没 dataset_id      -> missing_dataset_id
   workflow 节点没 workflow_id    -> missing_workflow_id
```

这就是 M1/设计文档里“改②：胖节点用校验兜底”的落地——IR 结构故意扁平（所有 kind 共用一个 struct），类型安全靠这里补回来：

```text
kind=start 却带 app_id 这种脏数据，结构层拦不住，校验层拦下。
```

### 7.6 checkEdges：边端点存在、无自环

```text
edge.source 不在节点集合 -> bad_edge
edge.target 不在节点集合 -> bad_edge
edge.source == edge.target -> self_loop
```

注意这里只查“单边自环”（A->A）。多节点成环（A->B->A）不在这查，交给下面的 `checkCycle`。

### 7.7 checkCycle：基于依赖图检测环（改①）

```go
func checkCycle(ir *dsl.IR, r *Result) {
    if dsl.HasCycle(dsl.BuildDeps(ir)) {
        r.add(SeverityError, "cycle", ...)
    }
}
```

这里完全复用 M1 的 `deps.go`：

```text
BuildDeps(ir) = 显式 edges ∪ ref bindings 推导的隐式边
HasCycle(deps) = Kahn 拓扑排序，visited != 总数 则有环
```

关键点（回顾 1.5）：**只看 edges 会漏 ref binding 形成的环**，所以必须用合并后的依赖图。

### 7.8 checkBindings：绑定校验（改③、改⑤）

这是最复杂的一个检查，逐条拆开。

外层遍历每个节点的每条 binding，同时记录“哪些端口被绑了”，最后查必填：

```go
for _, in := range n.Inputs {
    if in.Required && !bound[in.Name] {
        r.add(SeverityError, "required_not_bound", ...)  // 必填输入没绑
    }
}
```

单条 binding 的校验在 `checkOneBinding`，只对 `ref` 模式深入检查（literal/clear 不用查引用）：

```text
1. 推断 mode（缺省时：有 source_node 判 ref，否则 literal）
2. 非 ref 模式，直接返回
3. scope 非空          -> cross_scope_ref_forbidden（改⑤：MVP 禁止跨作用域）
4. source_node 不存在  -> ref_node_not_found
5. source_port 不存在  -> source_port_not_found
6. 类型不兼容          -> type_mismatch
```

第 3 步的作用域检查值得说明。M1 里 `Binding.Scope` 是预留字段（""/parent/root），MVP 阶段恒为空。这里就是那个“预留”的兑现：

```go
if b.Scope != "" {
    r.add(SeverityError, "cross_scope_ref_forbidden", ...)
    return
}
```

只要 binding 显式写了非空 scope，直接拦下——因为 MVP 还没实现嵌套作用域引用。

### 7.9 checkBindings 里的 batch 语义特例

这是 M3 校验器里最容易看懵的地方，单独讲。批处理（batch）节点有两个“运行期才产生、静态声明里没有”的特殊情况，校验器必须感知，否则会误报 `type_mismatch`。

**特例①：源节点开了 batch，引用它的聚合产物 `items`/`count`**

```go
func srcBatchOutput(src *dsl.Node, port string) bool {
    if src.Batch == nil || !src.Batch.Enable {
        return false
    }
    return port == "items" || port == "count"
}
```

batch 节点跑完，运行期会产出聚合结果 `{items, count}`（见 M4 scheduler）。这两个端口即使没在 `Outputs` 里静态声明，也合法；类型按 `array` 处理。所以下游 ref `clf_0.items` 不会报 `source_port_not_found`。

**特例②：目标节点开了 batch，绑定的是它的“迭代源端口”**

```go
func isBatchIterateInput(n *dsl.Node, port string) bool {
    if n.Batch == nil || !n.Batch.Enable {
        return false
    }
    item := n.Batch.ItemName
    if item == "" {
        item = n.Batch.SourcePort
    }
    return port == item
}
```

batch 节点会把上游的 `array` **逐项拆开**注入。所以源是 `array`、目标 input 声明是单个 `object`，**不算** `type_mismatch`（因为运行期传进去的是数组里的一个元素，不是整个数组）：

```go
if isBatchIterateInput(n, b.Port) && out.Type == "array" {
    return  // array -> 元素类型，合法，不报错
}
```

但反过来——batch 聚合输出 `items`（恒为 array）如果接到一个声明为 `string` 的目标端口，**仍然报** `type_mismatch`：

```go
if in := findInput(n, b.Port); in != nil && in.Type != "" && !typeCompatible(in.Type, "array") {
    r.add(SeverityError, "type_mismatch", ...)  // items 是 array，目标不是 array -> 报错
}
```

`typeCompatible` 的宽松规则：

```go
func typeCompatible(target, actual string) bool {
    return target == actual || target == "any" || target == ""
}
```

第 9 节的 `batchIR` 测试专门覆盖这两个特例，建议对照着看。

### 7.10 checkReachability：可达性（唯一的 warning）

```go
func checkReachability(ir *dsl.IR, nodes map[string]*dsl.Node, r *Result)
```

它做的事：

```text
1. BuildDeps 拿到依赖图（前驱关系）
2. 翻成正向邻接 next：pre -> [后继]
3. 找到 start 节点，从它 BFS
4. 除 start 外，任何 BFS 到不了的节点 -> warning unreachable_node
```

为什么是 warning 而不是 error？因为孤立节点不会让图“跑崩”，只是白搭了不会执行——提示即可，不阻断。测试 `TestValidate_UnreachableWarning` 就是加一个没有入边的孤立 application 节点，期望拿到这个 warning。

⚠️ 实现与注释的一处出入（如实记录）：该函数的注释写的是“校验除 start 外节点可达、**除 end 外能到达 end**”，但当前代码只实现了前半句（从 start 正向可达）；“能否到达 end”的反向可达性检查**并未实现**。也就是说，一个“从 start 能走到、但走不到任何 end 的死胡同节点”当前不会被 `unreachable_node` 捕获。这是可以在后续补强的点（见第 11 节）。

### 7.11 校验器当前的两个盲区（重要）

前面十小节讲的都是“校验器查了什么”。这一节反过来讲“校验器**没查**什么”——两个当前会漏过、要到 M4 执行期才暴露的盲区。理解它们，才能明白 M3 的“0 error”并不等于“一定能跑通”。

#### 盲区①：condition 节点几乎零专项校验

`condition` 在 `supportedKinds` 里，所以节点类型本身合法。但除此之外，**校验器对 condition 的分支逻辑不做任何检查**：

```text
checkKindAndFields：只查 kind 受支持 + 专属 ID 字段，不碰 Branches
checkBindings：     只遍历 Bindings，Branches 不是 Binding，不在其视野内
其余检查：          都与 branches 无关
```

也就是说，以下这些坏 condition 全部能通过 M3 校验：

```text
Branches 为空（一个分支都没有）
Comparator 拼错（如写成 "greater" 而不是 "gte"）
Condition.LeftNode / LeftPort 指向不存在的节点或端口
Branch.Index 与 edge 的 source_port 对不上（分支序号错位）
```

后果是这些问题**全部推迟到 M4 执行期**才炸。最典型的：branches 为空的 condition，要到 `ConditionExecutor.Execute` 才报错（见 M4 讲义 6.4）：

```go
branches, ok := ec.Node.Data.NodeParam["branches"].([]any)
if !ok || len(branches) == 0 {
    return nil, fmt.Errorf("condition node %s has no branches", ec.Node.ID)
}
```

comparator 拼错更隐蔽——`compare` 遇到未知比较器直接返回 `false`（见 M4 讲义 6.4 的 `compare`），于是该分支**静默失活**，不报错、不命中，工作流走向 default 或被剪枝跳过。这种“不报错但行为不对”的问题，恰恰是静态校验最该拦、当前却漏掉的。

对比一下 M1 与 M4 对 branches 的处理，能看清这个盲区的位置：

```text
M1 render：把 IR.Branches 渲染进 DSL 的 nodeParam.branches
           （早期曾有丢弃 branches 的 bug，M4 用 TestRun_RenderedConditionExecutes 守住）
M3 validate：完全不看 branches   <- 盲区就在这里
M4 execute：真正消费 branches，坏了才报
```

#### 盲区②：literal binding 完全不校验类型

回看 `checkOneBinding` 的第二步（7.8）：

```go
if mode != dsl.BindModeRef {
    return   // 非 ref（literal / clear）直接返回，后面全部跳过
}
```

这一行 `return` 意味着：**literal 绑定只要不是 ref，就不做任何后续校验**。具体漏掉的是：

```text
value 与 value_type 不一致
  —— value_type 声明 number，但 value 是字符串 "abc"，不报错
literal 值与目标 input 声明类型不匹配
  —— 目标 input 声明 type=integer，literal 却给了 object，不报错
```

注意这里有个不对称，值得记牢：

```text
ref 绑定：会走 type_mismatch 检查（上游 output 类型 vs 目标 input 类型）
literal 绑定：同样的类型冲突，完全不查
```

所以同一个“类型接错”的错误，用 ref 写会被 M3 拦下，用 literal 写就漏过去了。

需要澄清一点，避免矫枉过正：literal binding **并非完全不参与校验**。`checkBindings` 外层对每条 binding（不分 mode）都会登记 `bound[b.Port] = true`，所以 literal 绑定能正常满足“必填输入必须绑定”（`required_not_bound`）。它只是**不参与类型校验**而已。

也别和第 6 节的 `ValidateOutputs` 搞混：

```text
ValidateOutputs：查“节点实际输出值”的类型，运行期、针对 output
literal 类型校验：查“编辑期写死的输入常量”的类型，静态、针对 input
                 —— 当前无人负责
```

#### 两个盲区的共性

```text
它们都让“静态可判定的错误”漏到了运行期：
condition 分支错 -> M4 执行 condition 时才炸或静默失活
literal 类型错   -> M4 节点消费该常量时才可能出问题（甚至静默传下去）
```

这与 M3 的立身之本——“不运行就把坏图挡下”——是相悖的。两者都属于“校验器本应覆盖、当前留白”的明确缺口，已记入第 11 节增强项。

## 10. 变量池在运行时如何被串起来（承上启下）

M3 只造了变量池这块“内存”，真正往里读写是 M4 调度器的事。提前看一眼串联关系，有助于理解 M3 为什么这么设计（`scheduler.go`）：

```text
节点执行前：
  inputs, err = builder.ResolveInputs(node, c.pool)
    —— 把节点的 ref binding 通过 pool.Resolve(nodeID, port) 变成具体值

节点执行：
  ec := &nodes.ExecContext{Node: node, Inputs: inputs, Pool: c.pool, RunID: c.runID}
  result, execErr := 执行器.Run(ec)

节点执行后：
  execErr != nil -> c.pool.SetError(id, "NODE_ERROR", ...)  // 失败写错误变量
  execErr == nil -> c.pool.SetOutputs(id, result.Outputs)   // 成功写输出
```

于是一条数据在图里的流动是：

```text
上游节点跑完 -> SetOutputs 写进变量池
                     |
                     v
下游节点跑前 -> ResolveInputs 通过 Resolve 从变量池取值
                     |
                     v
                下游节点拿到具体 inputs 执行
```

这也解释了 M3 的两个设计选择：

```text
为什么变量池 key 用 DSL ID？因为运行期节点是 DSL 节点。
为什么 Get 要支持路径？因为 ref 的 source_port 可能是 response.metadata.model 这种深层引用。
```

## 11. 当前 M3 的设计边界和后续增强

当前已经完成：

```text
1. VariablePool：两层 map + RWMutex，Set/SetOutputs/SetError/Get/Resolve/Has/Snapshot
2. 路径解析：parsePath + walkPath，支持 a.b、a[0]、a.b[0].c 混合，对标 PaiFlow
3. 系统错误变量：errorCode / errorMessage 自动可用
4. 输出校验：ValidateOutputs 按声明查类型与必填
5. 静态校验器：结构/起止/字段合法性/边/环/绑定/引用/类型/作用域/可达性
6. batch 语义感知：聚合输出 items/count、迭代输入 array->元素 不误报
7. 执行依赖复用：checkCycle/checkReachability 都基于 edges∪bindings
```

当前还可以增强：

```text
1. 补齐反向可达性：检查“从节点能否到达 end”，捕获死胡同节点
   （当前 checkReachability 的注释提到但代码未实现，见 7.10）。
2. condition 专项校验（盲区①，见 7.11）：branches 非空、comparator 合法、
   left_node/left_port 存在、Branch.Index 与 edge 的 source_port 对齐。
   —— 让 condition 的坏分支在保存期被拦，而非 M4 执行期才炸或静默失活。
3. literal binding 类型校验（盲区②，见 7.11）：checkOneBinding 在 literal 分支
   补 value 与 value_type、以及 literal 值与目标 input 类型的比对。
   —— 消除“同样类型错误，ref 拦得住、literal 漏过去”的不对称。
4. Snapshot 做真正的深拷贝（含嵌套 map/slice），支持大对象安全快照。
5. type_mismatch 目前是精确相等比对（string != integer），可引入
   更细的兼容规则（如 integer 可赋给 number）。
6. 变量池可加“端口维度”的读写审计，配合 node-debug 定位“谁没给我传值”。
```

上面第 1~3 条都属于“静态可判定、当前却漏到运行期”的缺口，优先级最高：反向可达性是唯一“注释承诺了但代码没做”的检查项；condition 与 literal 两个盲区则直接违背 M3“不运行就挡下坏图”的立身之本——三者补齐后，M3 的“0 error”才更接近“能跑通”的真实保证。

---

## 12. 一句话总结 M3

```text
M3 是工作流的“运行前守门 + 运行时内存”两件套：
校验器 Validator 吃编辑态 IR（服务端先 DSL->ToIR），在不运行的前提下把结构、字段、
绑定、引用、类型、环等坏图拦在保存/发布之前，error 必须清零、warning 仅提示；
变量池 VariablePool 是一次运行的并发安全共享内存（DSL 节点 ID -> 端口 -> 值，不落库），
支持 result.segments[0].text 这种路径引用，节点跑完写输出、跑前按 ref 取值；
两者共用 M1 的执行依赖公式 edges ∪ bindings，杜绝“引用了非 edge 上游却被提前调度”。
```
