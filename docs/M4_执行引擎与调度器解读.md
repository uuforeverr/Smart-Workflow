# M4 执行引擎与调度器解读

本文用于精读 Smart-Workflow 的 M4 代码，覆盖：

- `internal/engine/run.go`：引擎入口 `Engine.Run(ctx, runID)`
- `internal/engine/builder/plan.go`：DSL → 可执行 Plan 编译器
- `internal/engine/builder/resolve.go`：ref/literal 输入解析
- `internal/engine/scheduler/scheduler.go`：依赖驱动的并发调度器
- `internal/engine/scheduler/batch.go`：批处理包装
- `internal/engine/nodes/*.go`：节点执行器（start/end/condition/http/code…）与注册表
- `internal/engine/debug.go`：单节点隔离调试 DebugNode
- `internal/engine/scheduler/scheduler_test.go` / `run_integration_test.go`：M4 测试

M4 的核心目标：

```text
把 M2 存的 DSL、M3 校验过的图，真正“跑起来”：
按依赖顺序并发调度节点，节点间通过 M3 的变量池传值，
每个节点和整次运行的快照落进 M2 的 workflow_run / node_run 表。
```

先给结论：

```text
M4 是 M1~M3 的收敛点。
M1 定义“工作流是什么”（IR/DSL），
M2 把它存下来（MySQL），
M3 在运行前挡住坏图（validator）+ 准备运行时内存（varpool），
M4 把这些拼起来，变成一次真正的执行。
```

---

## 1. 先回答几个最容易混淆的问题

### 1.1 为什么引擎入口是 `Run(ctx, runID)`，而不是 `Run(ctx, dsl)`？

因为要让**同步 HTTP handler** 和**异步 worker** 复用同一个入口，零重构。

看签名（`run.go`）：

```go
func (e *Engine) Run(ctx context.Context, runID string) error
```

它只吃一个 `runID`，其余全从数据库里的 `workflow_run` 记录读。这是刻意设计的“纯函数化”入口，plan.md 里明确写了这条约束：

```text
引擎入口设计为异步可复用纯函数：engine.Run(ctx, runID) error
  —— 不关心谁调它（同步 handler 直接调 / worker 队列调，同一入口）
  —— 状态、输入、输出全部落 workflow_run/node_run，不依赖调用方内存
  —— 避免 M9 加队列时重构调度入口
```

于是调用方只要先把 run 记录落库（`status=pending`），再把 `runID` 交给引擎即可：

```text
M6 同步 handler：POST /runs 落 pending -> 后台 goroutine 调 engine.Run(ctx, runID)
M9 异步 worker： 把同一个 runID 丢进 asynq 队列 -> worker 调 engine.Run(ctx, runID)
```

两条路径共用一个 `Run`，核心逻辑不用改。这就是 M2 为什么早早建好 `workflow_run` 表——它是引擎和调用方之间的“契约载体”。

### 1.2 引擎怎么知道该跑哪个版本的 DSL？

看 `run.Version`，规则和 M2 讲的版本语义完全对齐（`run.go` 的 `loadDSL`）：

```text
version == -1  -> 读 workflow.draft_dsl（草稿调试，DraftVersion）
version  > 0   -> 读 workflow_version.dsl（指定发布快照）
```

M2 文档里那句“version = -1 读取 draft_dsl 的约定在 M4 中使用”，兑现的就是这里：

```go
const DraftVersion = -1

if version == DraftVersion {
    wf, _ := e.store.Q.GetWorkflow(ctx, workflowID)
    raw = wf.DraftDsl          // 草稿，可变，不缓存
} else {
    ver, _ := e.store.Q.GetWorkflowVersion(...)
    raw = ver.Dsl              // 发布快照，不可变，可缓存
}
```

注意一个 M9-a 顺带做的优化：**已发布版本不可变，所以可以缓存**；草稿可变，不缓存。

```go
cacheable := version != DraftVersion && e.cache != nil
```

这正好呼应 M2 的核心结论——“workflow_version 只追加不修改”，不可变才敢缓存。

### 1.3 调度器是怎么决定节点执行顺序的？和 M3 的依赖图是一套吗？

思路一样（`edges ∪ ref bindings`），但**是另一套独立实现**，作用在 DSL 层。

M3 的 `dsl.BuildDeps` / `dsl.HasCycle` 作用在 **IR** 上，服务于静态校验。M4 的 `builder.Build` 作用在 **DSL** 上，产出真正拿去调度的 `Plan`：

```text
M3 validator：IR -> dsl.BuildDeps(ir) -> dsl.HasCycle    （编辑期校验）
M4 builder：  DSL -> builder.Build(dsl) -> hasCycle(plan) （运行前编译）
```

两者公式一致——都把“ref 数据引用”补成隐式控制边（`plan.go`）：

```go
// 生效边 = 显式边 + 隐式 ref 边（同一 (source,target) 去重，显式优先）
for _, n := range d.Nodes {
    for _, in := range n.Data.Inputs {
        if in.Schema.Value.Type != dsl.DSLValueRef { continue }
        rc, _ := refContentOf(in.Schema.Value.Content)
        // 若 rc.NodeID -> n.ID 这条边还没有，补一条隐式边
        edges = append(edges, dsl.DSLEdge{SourceNodeID: rc.NodeID, TargetNodeID: n.ID})
    }
}
```

为什么要两套？因为校验吃 IR（可读 ID、扁平 binding），执行吃 DSL（执行态 ID、内联 value），两层结构不同，各自算一遍最直接。代价是环检测逻辑重复了一次——这是可以合并的技术债（见第 10 节）。

### 1.4 调度器是多线程的吗？状态为什么不用加锁？

是并发的，但用了一个巧妙的模型：**单线程协调器 + 多 goroutine worker**。

关键在 `coord.loop`（`scheduler.go`）：

```text
loop（单线程）：独占所有 states / ready 队列 / 计数器
  |
  |  go execNode(...)  派发到 worker goroutine
  v
worker（多个并发）：只干“解析输入 -> 执行节点 -> 回传一个 event”
  |
  |  done <- event   通过 channel 把结果送回
  v
loop：从 done channel 收 event，串行更新状态、决定下一批就绪节点
```

也就是说：

```text
真正“并发”的只有节点执行本身（execNode 里的 I/O）。
所有状态变更都回到单线程 loop 里串行处理。
```

所以 `nodeState`（status/result/计数器）不需要锁——只有 loop 一个 goroutine碰它。代码注释点破了这个设计：

```go
// loop 是单线程协调器：拥有全部 states/ready/计数，workers 仅回传 event。
seq int64 // 单调事件序号，仅在单线程 loop 内自增，无需锁
```

需要锁的只有两个**跨 goroutine 共享**的东西：变量池（M3 的 `RWMutex`）和注册表（`nodes.Registry` 的 `RWMutex`）。这也解释了 M3 为什么给变量池加读写锁——正是为 M4 的并发 worker 准备的。

### 1.5 一个节点失败了，整个工作流会怎样？

当前实现是**失败即中断整图**（`ErrStrategyInterrupted`）。

`loop` 收到 `StatusFailed` 的 event 后（`scheduler.go`）：

```go
if e.status == nodes.StatusFailed {
    if c.abortErr == nil {
        c.abortErr = fmt.Errorf("node %s failed: %w", e.id, e.err)
    }
    c.cancel() // 通知在途 worker 取消；停止派发新节点，只等在途排空
    continue
}
```

做了三件事：

```text
1. 记录 abortErr（第一个失败原因）
2. c.cancel() 取消 context，通知所有在途 worker 尽快停
3. 不再派发新节点，只等在途的排空，然后 loop 退出
```

注意 DSL 的 `RetryConfig` 其实预留了三种失败策略（M1 讲过）：

```text
ErrStrategyInterrupted  = 0  中断整个工作流   <- 当前只实现了这个
ErrStrategyFailBranch   = 1  走失败分支       <- 未接
ErrStrategyCustomReturn = 2  返回自定义兜底输出 <- 未接
```

M4 只实现了策略 0。fail-branch 和 custom-return 是明确的后续增强点（第 10 节）。

### 1.6 batch（批处理）节点是怎么执行的？

它是**包在任意执行器外面的一层通用包装**，不是一种新节点类型。

这点和 M3 校验器里的 batch 语义特例是同一件事的两面。执行侧看 `runNode`（`batch.go`）：

```text
没开 batch  -> runWithRetry(exec, ec)           普通执行
开了 batch  -> 取迭代源数组 -> 对每个 item：
                复制 inputs，把迭代变量替换成单个 item
                runWithRetry 跑一遍
              -> 聚合所有结果为 {items:[...], count:n}
```

关键代码：

```go
for i, item := range list {
    iterInputs := copy(ec.Inputs)
    iterInputs[spec.itemName] = item          // 逐项替换迭代变量
    res, _, attempt, err := runWithRetry(ctx, exec, iterCtx, cfg)
    items = append(items, res.Outputs)
}
return &nodes.NodeResult{Outputs: map[string]any{
    "items": items,
    "count": len(items),
}}, ...
```

这就解释了 M3 校验器里两个特例的由来：

```text
M3 特例①：源节点 batch，聚合输出 items/count 未声明也合法
  —— 因为 items/count 是这里运行期才产生的
M3 特例②：目标节点 batch，array -> 元素类型 不算 type_mismatch
  —— 因为这里把数组逐项拆开，注入的是单个 item
```

设计上强调一句（`batch.go` 注释）：batch 不改变 DAG 结构，一个 batch 节点在 `node_run` 里仍是**一条记录**，聚合结果作为它的单条输出。

## 2. M4 的整体架构

一次运行的完整生命周期：

```text
调用方（M6 handler / M9 worker）
   |  先落库 workflow_run(status=pending)，拿到 runID
   v
Engine.Run(ctx, runID)                      run.go
   |  1. 读 run 记录，标记 running
   |  2. loadDSL：按 version 读草稿或发布快照（可缓存）
   |  3. decodeInput：解析运行入参
   v
builder.Build(dsl)  -> Plan                  builder/plan.go
   |  建节点表 + 合并 edges∪ref + 建邻接 + 查环
   v
scheduler.Run(plan, pool, opts) -> Result    scheduler/scheduler.go
   |  单线程 loop 派发 + 多 worker 并发执行
   |  每个节点：ResolveInputs -> registry.Get -> runNode(retry/batch) -> 写池
   v
persistFinal                                 run.go
   |  事务内批量写 node_run + 更新 workflow_run 终态
   v
返回 error（nil=成功）
```

核心文件与职责：

```text
run.go                引擎门面：读 run、装配、调度、落库、发事件
builder/plan.go       DSL -> Plan（依赖图 + 邻接表 + 起止节点）
builder/resolve.go    节点输入解析：ref 查变量池 / literal 直取
scheduler/scheduler.go 依赖驱动并发调度 + condition 剪枝 + retry + 中断
scheduler/batch.go    batch 包装：逐项执行 + 聚合
nodes/node.go         NodeExecutor 接口 + Registry 注册表
nodes/register.go     NewDefaultRegistry：按 config 装配内置执行器
nodes/*.go            各类型执行器：start/end/condition/http/code/application/dataset
debug.go              单节点隔离调试（关重试 + 断言）
```

一句话概括分层：

```text
Engine  管“一次运行的生命周期与落库”。
Builder 管“把 DSL 编译成能调度的图”。
Scheduler 管“按依赖并发跑、处理分支/重试/失败”。
Nodes   管“单个节点具体怎么执行”。
```

## 3. Engine.Run：一次运行的主干

源码：`internal/engine/run.go`

### 3.1 Engine 结构

```go
type Engine struct {
    store       *mysql.Store
    registry    *nodes.Registry   // 节点执行器注册表（实例化，非全局）
    logger      *zap.Logger
    cache       DSLCache          // 定义缓存（M9-a），可 nil
    emitter     runevent.Emitter  // 运行事件发射器（M9-b SSE），可 nil
    Concurrency int               // 并发上限，默认 8
}
```

构造（`New`）做了两件关键装配：

```go
func New(store *mysql.Store, sidecarURL string) *Engine {
    cfg := nodes.Config{SidecarURL: sidecarURL}  // 打通 config -> code 节点 sidecar 地址
    if store != nil {
        res := &storeResolver{store: store}       // application/dataset 的 store 解析器
        cfg.AppResolver = res
        cfg.DatasetResolver = res
    }
    return &Engine{
        store:    store,
        registry: nodes.NewDefaultRegistry(cfg),
        ...
        Concurrency: 8,
    }
}
```

这体现了 M5 反思后的一个重要改造：**注册表实例化，不再是包级全局**。好处 M3/M5 都提过——`-race` 通过、并行测试互不污染、能按配置注入不同的 sidecar 地址。

### 3.2 Run 的七个阶段

`Run` 的每一步都打了 `run stage:` 日志，串起来就是执行骨架：

```text
1. load run record     GetWorkflowRun(runID)
2. mark running        updateRun(status=running, started_at=now)
3. decode input        decodeInput(run.Input)
4. load dsl            loadDSL(workflowID, version)  可缓存
5. build plan          builder.Build(dsl)
6. schedule            scheduler.Run(plan, pool, opts)
7. persist final       persistFinal(node_run 批量 + workflow_run 终态)
```

失败处理很讲究，分了两种“死法”：

```text
failRun（run.go）      —— 跑起来后某步失败：落 failed 终态 + 已执行节点的 node_run
FailRunWithError（墓碑） —— 压根没进 Run 主体或后台 goroutine panic：
                           强制打 failed，避免 run 永久卡在 pending/running
```

第二个是 M6 反思补强（TD-8）的兜底，保证任何异常路径下 run 都有终态，不会“僵尸挂起”。

### 3.3 persistFinal：为什么放在一个事务里？

```go
func (e *Engine) persistFinal(...) error {
    return e.store.WithTx(func(q *gen.Queries) error {
        for _, n := range result.Nodes {
            q.CreateNodeRun(...)   // 逐个节点快照
        }
        q.UpdateRunStatus(...)     // 整次运行终态
        return nil
    })
}
```

用 M2 讲的 `store.WithTx` 事务封装，把“N 条 node_run + 1 条 workflow_run 更新”绑成原子操作：

```text
要么全部落库（node_run 快照 + run 终态一致），
要么全部回滚（不会出现“run 成功了但节点快照缺一半”的脏状态）。
```

写入的字段正好填满 M2 预留的 `node_run` 表：input/output/error/status/attempt/cost_ms/started_at/finished_at。M2 那句“M4 执行引擎会写入每个节点的 input/output/error/status/耗时/尝试次数”，落地就在这里。

## 4. Builder：DSL 编译成可执行 Plan

源码：`internal/engine/builder/plan.go`

### 4.1 Plan 结构

```go
type Plan struct {
    Nodes    map[string]dsl.DSLNode      // dslNodeID -> 节点
    Edges    []dsl.DSLEdge               // 生效边集（含隐式 ref 边）
    InEdges  map[string][]dsl.DSLEdge    // 入边邻接
    OutEdges map[string][]dsl.DSLEdge    // 出边邻接
    StartIDs []string
    EndIDs   []string
}
```

Plan 就是“调度器直接能用的图”：节点表 + 双向邻接表 + 起止节点索引。

### 4.2 Build 的四步

```text
1. 建节点表：查空 ID / 重复 ID（和 M3 校验器同类检查，运行前再兜一次）
2. 合并生效边 = 显式 edges ∪ ref 隐式边（去重，显式优先）
3. 建 InEdges/OutEdges 邻接表 + 收集 StartIDs/EndIDs
4. hasCycle 查环，有环直接报错
```

第 2 步是 Plan 的灵魂，也是 M1 §10.6 “binding 即隐式依赖”的执行态落地。举例：

```text
DSL 里只有边 start -> end
但 end 的某个 input ref 了 http 节点的输出
Build 会自动补一条 http -> end 的隐式边
=> 调度时 end 一定等 http 先跑完
```

`refContentOf` 还做了个务实的兼容：ref 的 content 可能是内存构造的 `dsl.RefContent`，也可能是 JSON 反序列化出来的 `map[string]any`（键 `nodeId`/`name`）。两种都认——因为 DSL 既可能是代码里 new 的，也可能是从 MySQL JSON 列读出来的。

### 4.3 输入解析 ResolveInputs

源码：`internal/engine/builder/resolve.go`

节点执行前，调度器调它把内联的 binding 变成具体值：

```go
switch v.Type {
case dsl.DSLValueRef:
    rc, _ := refContentOf(v.Content)
    val, err := pool.Resolve(rc.NodeID, rc.Name)  // 从 M3 变量池按路径取
    out[in.Name] = val
case dsl.DSLValueLiteral:
    out[in.Name] = v.Content                       // 常量直取
default:
    // 空 Value（clear/未绑定）跳过
}
```

这里直接用了 M3 变量池的 `Resolve`（就是 `Get` 的别名），`rc.Name` 可以是 `json.message` 这种路径。M3 讲的路径解析（`result.segments[0].text`），消费方就是这一行。

一个特例：**start 节点不走 ResolveInputs**。它的输入是整个工作流的运行入参，由调度器直接注入（`scheduler.go`）：

```go
if nodeType == dsl.KindStart {
    inputs = c.runInput          // 运行入参直接作为 start 的输入
} else {
    inputs, err = builder.ResolveInputs(node, c.pool)
}
```

## 5. Scheduler：依赖驱动的并发调度

源码：`internal/engine/scheduler/scheduler.go`

这是 M4 最核心、最烧脑的部分。前面 1.4 已讲清“单线程 loop + 多 worker”模型，这里补齐调度细节。

### 5.1 nodeState：每个节点的调度账本

```go
type nodeState struct {
    status     string
    result     *nodes.NodeResult
    ...
    totalIn    int   // 入边总数
    unsettled  int   // 尚未“结算”的入边数（上游还没终态）
    liveIn     int   // 已结算且“存活”的入边数
    branchIn   int   // 来自 condition 分支的入边数
    liveBranch int   // 存活的分支入边数
    decided    bool  // 已决定运行或跳过，防重复路由
}
```

这几个计数器是理解 condition 剪枝的钥匙。核心思想：

```text
每条入边有两种命运：live（存活，上游成功且分支命中）或 dead（死掉）。
一个节点的所有入边都“结算”完（unsettled==0）后，才决定它 run 还是 skip。
```

### 5.2 loop 主循环

```text
种子：所有无入边的节点（start / 孤立节点）直接进 ready
循环：
  A. 只要 ready 非空、在途 < 并发上限、没 abort：派发节点到 worker
  B. 在途为 0 -> 退出（正常跑完，或 abort 后排空）
  C. 从 done channel 收一个 event：
     - 更新该节点状态
     - 发 node_end 事件
     - 若失败：记 abortErr + cancel，只等在途排空
     - 若成功：propagate 结算出边，可能产生新 ready
```

并发上限就是这段的 `c.inFlight < c.concurrency`——用“在途计数”做信号量，不用额外的 semaphore 库。

### 5.3 propagate：condition 剪枝与级联跳过

节点终态后，`propagate` 结算它的所有出边：

```go
for _, e := range c.plan.OutEdges[cur] {
    live := succeeded && (!isCond || e.SourceHandle == branch)
    tgt.unsettled--
    if live {
        tgt.liveIn++
        if c.isBranchEdge(e) { tgt.liveBranch++ }
    }
    if tgt.unsettled == 0 {          // 该下游所有入边都结算了
        tgt.decided = true
        if !tgt.shouldRun() {
            tgt.status = StatusSkipped
            queue = append(queue, e.TargetNodeID)  // 级联跳过下游
        } else {
            *ready = append(*ready, e.TargetNodeID) // 就绪，可运行
        }
    }
}
```

`live` 的判断是 condition 剪枝的精髓：

```text
普通节点成功       -> 所有出边 live
condition 节点成功 -> 只有 SourceHandle == 命中分支 的出边 live，其余 dead
```

`shouldRun` 决定 run 还是 skip：

```go
func (s *nodeState) shouldRun() bool {
    if s.branchIn > 0 {
        return s.liveBranch > 0   // 有分支入边：至少一条分支存活才跑
    }
    return s.liveIn > 0            // 普通节点：至少一条入边存活才跑
}
```

“级联跳过”是关键收尾：一个节点被 skip 后，它也进 queue，继续结算它的出边——于是“死分支”会一路 skip 到底，不会留下卡住的下游。测试 `TestRun_ConditionBranchSkipsUnmatchedBranch` 正是验证这个：score=0.9 命中分支 0，`end::pass` 跑、`end::fail` 被 skip。

### 5.4 execNode + runWithRetry：worker 里发生了什么

worker goroutine 干的活（`execNode`）：

```text
1. 解析输入（start 注入入参 / 其余 ResolveInputs）
2. registry.Get(nodeType) 取执行器，取不到直接 failed
3. runNode（batch 包装）-> runWithRetry 真正执行
4. 成功：pool.SetOutputs(id, outputs)；失败：pool.SetError(id, "NODE_ERROR", msg)
5. 把结果打包成 event 送回 done channel
```

`runWithRetry` 的重试语义：

```go
maxTries := 1
if cfg.ShouldRetry && cfg.MaxRetries > 0 {
    maxTries = 1 + cfg.MaxRetries
}
for attempt = 1; attempt <= maxTries; attempt++ {
    nctx, cancel := context.WithTimeout(ctx, timeout)  // 每次尝试独立超时
    res, err := exec.Execute(nctx, ec)
    cancel()
    if err == nil { return res, ... }
    if ctx.Err() != nil { break }   // 父 ctx 已取消（整图 abort），不再重试
}
```

两个要点：

```text
每次 attempt 有独立的 timeout（默认 60s，来自 RetryConfig.Timeout）。
父 ctx 一旦被 cancel（别的节点失败触发整图中断），立即停止重试。
```

这正好接上 M1 讲的 `RetryConfig` 默认值：`Timeout=60, ShouldRetry=false, MaxRetries=0`——默认不重试、单次 60s 超时。

### 5.5 result：输出怎么合并

```go
func (c *coord) result() *Result {
    outputs := map[string]any{}
    for _, endID := range c.plan.EndIDs {
        st := c.states[endID]
        if st.status == StatusSucceeded && st.result != nil {
            for k, v := range st.result.Outputs {
                outputs[k] = v          // 合并所有成功 End 节点的输出
            }
        }
    }
    ...
}
```

整次运行的最终输出 = **所有成功 end 节点输出的合并**。所以多 end 分支场景下，被 skip 的 end 不贡献输出，只有命中分支的 end 结果进 `workflow_run.output`。

## 6. 节点执行器：统一接口 + 各自实现

源码：`internal/engine/nodes/`

### 6.1 统一接口 NodeExecutor

```go
type NodeExecutor interface {
    Type() string
    Execute(ctx context.Context, ec *ExecContext) (*NodeResult, error)
}
```

所有节点类型都实现这一个接口，调度器不关心具体类型，只 `registry.Get(type).Execute(...)`。这是典型的策略模式，也是 M4 能“加节点类型不改调度器”的原因。

```go
type ExecContext struct {
    Node   dsl.DSLNode
    Inputs map[string]any        // 已解析好的输入值
    Pool   *varpool.VariablePool // M3 变量池
    RunID  string
}
type NodeResult struct {
    Outputs map[string]any
    Branch  string // 仅 condition 用：命中的分支句柄
}
```

### 6.2 M4 交付的核心节点

plan.md 的 M4 只要求 `start / end / condition / http` 四个（code 是 M5，application/dataset 是 M10，但都复用同一接口）：

| 节点 | 文件 | 做什么 |
|---|---|---|
| **start** | start.go | 把运行入参原样作为输出（下游据此 ref） |
| **end** | end.go | 收集输入；有 `template` 时按 `{{port}}` 渲染出 `output` |
| **condition** | condition.go | 按 branches 求值，返回命中的 `Branch` 句柄 |
| **http** | http.go | 调外部 API，输出 status_code/body/json |
| code | code.go | 把代码+inputs 发 Python sidecar（M5） |
| application | application.go | 按 app_id 解析后委托 http/code（M10） |
| dataset | dataset.go | 按 dataset_id 读评测集行（M10） |

### 6.3 start / end：最简单的两个

`start` 就是恒等映射：

```go
func (StartExecutor) Execute(_ context.Context, ec *ExecContext) (*NodeResult, error) {
    out := copy(ec.Inputs)      // 输入原样作为输出
    return &NodeResult{Outputs: out}, nil
}
```

`end` 收集输入，可选套模板：

```go
if tpl, ok := ec.Node.Data.NodeParam["template"].(string); ok && tpl != "" {
    out["output"] = renderTemplate(tpl, ec.Inputs)  // {{answer}} -> inputs["answer"]
}
```

`renderTemplate` 是最朴素的字符串替换（`{{key}}` -> `inputs[key]`），http/end 都用它。测试里 `template: "{{answer}}"` + `answer` ref 到 `http::1.json.message`，最终 `output` 就是 HTTP 响应里的 message。

### 6.4 condition：分支求值

```go
func (ConditionExecutor) Execute(...) (*NodeResult, error) {
    branches := ec.Node.Data.NodeParam["branches"].([]any)
    for _, br := range branches {
        conds := br["conditions"]
        if allConditionsTrue(conds, ec.Inputs) {   // 一个分支内多条件取 AND
            idx := fmt.Sprintf("%v", br["index"])
            return &NodeResult{Branch: idx, ...}, nil  // 命中：返回分支序号
        }
    }
    return &NodeResult{Branch: "default", ...}, nil    // 无命中：default
}
```

要点：

```text
按 index 顺序取第一个“全条件为真”的分支。
一个分支内多个 condition 是 AND 关系。
返回的 Branch 就是 propagate 里用来剪枝的 SourceHandle。
比较器 compare 支持 eq/ne/gt/gte/lt/lte/contains，数值比较统一转 float64。
```

一个容易忽略的细节：condition 执行期只用 `left_port` 从 `ec.Inputs` 取值，**不用** M1 IR 里的 `left_node`——因为值在 ResolveInputs 阶段已经按 binding 取进 inputs 了，执行器只需按端口名读。

### 6.5 注册表装配 NewDefaultRegistry

```go
func NewDefaultRegistry(cfg Config) *Registry {
    r := NewRegistry()
    r.Register(StartExecutor{})
    r.Register(EndExecutor{})
    r.Register(ConditionExecutor{})
    r.Register(HTTPExecutor{})
    code := CodeExecutor{SidecarURL: cfg.SidecarURL}
    r.Register(code)
    if cfg.AppResolver != nil {        // 有 store 才注册 application
        r.Register(ApplicationExecutor{Resolver: cfg.AppResolver, Code: code, HTTP: HTTPExecutor{}})
    }
    if cfg.DatasetResolver != nil {    // 有 store 才注册 dataset
        r.Register(DatasetExecutor{Resolver: cfg.DatasetResolver})
    }
    return r
}
```

这个“按配置装配”的设计很关键：

```text
无 store 的纯单测：不注册 application/dataset，零副作用。
有 store 的真实运行：注入 storeResolver，application 节点能按 app_id 查库委托执行。
```

`ApplicationExecutor` 是个漂亮的复用案例（M10）：它不新造远程调用层，而是按应用的 `kind` 委托给已有执行器——`kind=http` 复用 HTTPExecutor，`kind=python` 复用 CodeExecutor，`kind=rpc` 明确未支持。这契合你项目里“复用优先”的哲学。

## 7. DebugNode：单节点隔离调试

源码：`internal/engine/debug.go`

这是 M6 会用到、但引擎侧提供的能力：不跑整图，只跑一个节点，拿即时反馈。

```go
func (e *Engine) DebugNode(ctx, node, inputs, costTargetSec) *DebugResult
```

它和正式 Run 的三个关键区别：

```text
1. 直接喂 inputs，不做变量池上游解析（隔离，不依赖上游节点）
2. 强制关重试（ShouldRetry=false, MaxRetries=0）—— 拿即时真实结果，不被重试掩盖
3. 用一个临时空 varpool.New()，RunID="debug"
```

为什么关重试？注释说得直白（抄 PaiFlow node_debug）：

```text
关重试：拿即时真实结果，不被重试掩盖问题。
```

调试时你想立刻看到“这个节点到底行不行”，重试会掩盖偶发失败，反而误导。

它还附带三条 MVP 断言，作为评测信号：

```text
status_success    节点是否成功
output_not_empty  输出是否非空
cost_under_sec    耗时是否在目标内（costTargetSec > 0 时才加）
```

这三条断言呼应了你 memory 里“评测优化流：指标固化”的偏好——把“节点健康”固化成可判定的断言。

## 8. 一条数据的完整流动（把 M1~M4 串起来）

用 M4 集成测试的 `start -> http -> end` 走一遍，看四个里程碑如何协作：

```text
【M1】IR 描述图，render 成 DSL：
  http 节点 input "q" ref start.query，
  end 节点 input "answer" ref http.json.message

【M2】DSL 存进 workflow_version.dsl，创建 workflow_run(version=1, status=pending)

【M3+M4】engine.Run(runID)：
  1. loadDSL 读出 version=1 的 DSL
  2. builder.Build：补隐式边 start->http->end，查环通过
  3. scheduler.Run：
     start 无入边 -> 就绪 -> 执行
       inputs = {query:"hello"}（运行入参）
       SetOutputs("start::1", {query:"hello"})        <- 写 M3 变量池
     start 成功 -> propagate -> http 就绪
       ResolveInputs：q = pool.Resolve("start::1","query") = "hello"
       HTTP GET /echo?q=hello -> {message:"hello"}
       SetOutputs("http::1", {status_code,body,json})
     http 成功 -> propagate -> end 就绪
       ResolveInputs：answer = pool.Resolve("http::1","json.message") = "hello"
                      （M3 路径解析在这里用上）
       template "{{answer}}" -> output="hello"
       SetOutputs("end::1", {answer,output})
  4. persistFinal：3 条 node_run + workflow_run(status=succeeded, output={output:"hello"})
```

集成测试 `TestM4_EngineRunPersistsSnapshots` 断言的正是这条链路：run 终态 succeeded、output.output=="hello"、3 条 node_run 都有时间戳和输出快照。

## 10. 当前 M4 的设计边界和后续增强

当前已经完成：

```text
1. Run(ctx, runID) 纯函数入口，同步/异步复用
2. version 语义：草稿(-1)/发布(N)，发布版可缓存
3. builder.Build：DSL -> Plan，edges∪ref 隐式依赖 + 环检测
4. 单线程协调 + 多 worker 并发调度（状态无锁）
5. condition 分支剪枝 + 级联跳过
6. retry（每次独立 timeout，父 ctx 取消即停）
7. batch 通用包装（逐项执行 + {items,count} 聚合）
8. 节点执行器接口 + 实例化注册表（按 config 装配）
9. node_run/workflow_run 事务化落库
10. DebugNode 单节点隔离调试 + 三断言
11. 运行事件 node_start/node_end/run_end（M9-b SSE 地基）
```

当前还可以增强：

```text
1. 失败策略只实现了 Interrupted(0)：
   ErrStrategyFailBranch(1) 走失败分支、ErrStrategyCustomReturn(2) 兜底输出 均未接。
   RetryConfig.CustomOutput 字段目前也没被消费。
2. 环检测重复实现：builder.hasCycle 与 M3 dsl.HasCycle 是两套（IR/DSL 各一）。
   可考虑统一或让 Build 前置复用 validator 结果。
3. 无“run 前 validation gate”（plan.md TD-10）：
   Build 只查了空 ID/重复 ID/坏边/环，M3 的完整校验（类型/必填/引用）
   当前不在 Run 主路径强制跑，坏图可能到执行期才暴露。
4. node_run 大对象未裁剪（M2 也提过）：output 直接整存，大 payload 会撑表。
5. 失败即 cancel 是“尽力而为”：在途 worker 靠 ctx 感知取消，
   不可取消的阻塞操作（如无 ctx 的第三方调用）仍需等其自然结束。
```

其中最值得优先补的是**失败策略 1/2** 和 **run 前 validation gate**——前者是执行语义的完整性，后者是把 M3 的校验能力真正接进执行主路径。

## 11. 一句话总结 M4

```text
M4 是 M1~M3 的收敛点：engine.Run(ctx, runID) 从库里读 run 记录、按 version 取草稿或
发布快照的 DSL，用 builder 编译成含隐式 ref 依赖的 Plan，交给“单线程协调器 + 多 goroutine
worker”的调度器依赖驱动地并发执行——节点间通过 M3 变量池传值、condition 按命中分支剪枝并
级联跳过、失败即中断整图（当前只实现 Interrupted 策略）、batch 作为通用包装逐项跑并聚合成
{items,count}——最后把每个节点和整次运行的快照事务化写进 M2 的 node_run/workflow_run，
入口纯函数化让 M6 同步 handler 与 M9 异步 worker 复用同一个 Run 而无需重构。
```
